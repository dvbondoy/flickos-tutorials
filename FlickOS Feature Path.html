FlickOS Feature Path

The thirteen stages a FlickOS feature goes through, in the order you do them, and where each one is taught. The tutorials live in ~/Documents; section and step numbers point into their READMEs. Each stage says when it's done, so you know when you can move on.

Decisions along the way

Each one is made in a design doc ADR, with its reason. The rule is the HIG's; the last column is where a tutorial works through it.

DecisionHow to decideRuleShown in
Does it need a spike?Only if a question can't be answered from the repo or Debian. If every part already works in another FlickOS program, write "no spike" and why.—snip-spike §0 · repo §2
Its own package, or part of one?Each setting has one owner. A view (Settings, Welcome) runs owners; it never becomes one.SET-1repo §2 (ADR-001)
On or off by default?Off. Nothing runs, is generated or is bound while off. Only an ADR that states the cost makes it the default.INT-9code §0
Depends or Recommends?Depends: the desktop breaks without it, and it reaches installed systems. Recommends: an app users may remove, new installs only. Try apt-get -s remove PKG.PKG-4repo §3
Which other packages change?A setting needs a Settings row or tile (flickos-control), History (flickos-control), maybe autostart (flickos-settings), both menus, and flickos-desktop's bump.INT-4 · SET-4 · PKG-3repo §6–7
A daemon?Only when a measured time budget needs one, signalled with pkill, and nothing while off.PERF-6—
Which version number?dch -i for a change; dch -v 2.0 when a stored value changes meaning.PKG-3code §11
Publish now?Only when the phase is complete for users. Code can sit in the repo until then ("not to be published before phase 2's Phone page").INT-4repo §15

Gates you never skip

  • A new version for every content changedch -i -D trixie "…", never by hand, never UNRELEASED. Check repo/public/pool first: a published version is frozen.
  • Tests never touch the hostFake every path the program uses. Run leak-check.py whenever it reads or writes somewhere new.
  • Cross-package tests run in the treepackages/build.sh builds packages alone and skips them. Run the tests in packages/NAME after changing either side.
  • Kill by PID on your own desktopYour computer runs a live FlickOS session. pkill -x by name hits your own programs.
  • Boot-test checks run in the VMThey change settings and close programs by name. Make sure each one fails against the old version.
  • Upgrade test before publishingOld version to new through apt: conffiles, Breaks, a new Depends, nothing kept back by surprise.
  • Recommends never reach installsA new Recommends is for new installs only. Anything installed systems must get is a Depends.
  • Read git status before committingAnything you didn't mean to change shows up there: build output, __pycache__, an experiment.
